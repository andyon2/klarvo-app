## What & Why

Replace the WebView2-based pill (FloatingBar) and live-preview overlays with **native Win32
layered windows** (tiny-skia for shapes, GDI for text, presented via `UpdateLayeredWindow(ULW_ALPHA)`).
Trigger: a WebView2 compositor bug stopped the overlay painting under occlusion. ADR-0021 supersedes
ADR-0020.

## What went well

- **Core goal achieved:** the pill stays painted under occlusion (10-1, AC-5) — the regression that
  motivated the whole epic is gone, confirmed in real daily use.
- **10-3 standby diagnosis = the gold standard for this codebase.** The "pill disappears after standby"
  defect was *measured, not guessed*: `PrintWindow(PW_RENDERFULLCONTENT)` returned the correct bitmap
  while `CopyFromScreen` showed zero pill pixels → DWM was no longer compositing the long-lived layered
  window. Microsoft-documented (KB 2667241), corroborated by independent expert analysis. Fix
  (recreate the window at each recording start) kills the defect class *by construction* — no fragile
  power-broadcast plumbing.
- **Adversarial code-review caught real defects before the human gate:** pill driven at only 4 of ~20
  state-emit sites (stuck on "Recording"); double-premultiplied teal border (~4× too faint); a
  use-after-free in `rebuild_dibs`; recreated pill losing the hotkey-mode badge.

## Recurring friction / lessons

1. **The native migration re-derives, one by one, everything the browser gave for free.**
   Occlusion-present (won, 10-1), but also: standby composition (regression → 10-3), DPI / text-scale
   honoring (regression → 10-4), font cascade, premultiplied alpha (10-2 patches). **This is the
   architectural lesson of ADR-0021:** the price of "native" is re-implementing the browser's
   compositor guarantees by hand. Every future overlay change inherits this burden.
2. **Guessing visual-fidelity bugs instead of measuring = 3× wrong.** 10-4 claimed "fixed" three times
   on the preview-size defect before the real root cause was *measured*: registry
   `HKCU\...\Accessibility\TextScaleFactor = 123%`, which WebView honors and GDI does not
   (15 × 1.25 DPI × 1.23 = 23px web vs 15 × 1.25 = 18px native → 18/23 = 0.78, exactly the measured
   ratio). Reinforces the standing rule: *measure surface fidelity with an objective pixel/registry
   metric before claiming a fix.* (cf. `feedback_verify_surface_fix_with_objective_pixel_metric`)
3. **The WSL win-gnu surface harness has blind spots.** It shims tauri/windows-rs and missed real MSVC
   errors twice (10-1: ~30 API signatures masked by the blocked check; 10-2: missing
   `use tauri::Listener` → E0599). Good for surface-compile, **not a substitute for Andi's real build.**
4. **"Too small" had three distinct root causes in 10-4** (DPI fix was a no-op · overlays are
   designed-small · TextScaleFactor). Each "too small" needed its own measurement — no single upstream.

## Key takeaways

1. Going native trades the browser's free compositor guarantees for hand-maintained ones — budget for
   re-deriving each (occlusion, standby, DPI, text-scale, alpha) on any overlay touch.
2. Visual-fidelity defects must be measured (pixel/registry), never guessed — the 10-3 method, not the
   10-4 first-three-attempts.
3. The WSL surface harness compiles, it does not validate the real MSVC/tauri build — the human Windows
   build remains the load-bearing gate.
