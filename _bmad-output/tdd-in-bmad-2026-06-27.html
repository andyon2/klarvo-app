Die Test-Kette einmal echt gefahren

Ziel: TDD als generische BMAD-Fähigkeit verstehen. Methode: die echte TEA-Kette atdd → dev → trace an einer lebenden Logik-Scheibe laufen lassen und festhalten, wo Stock-BMAD glatt läuft — und wo es bricht.

📅 2026-06-27 BMAD installiert 6.6.1-next.2 npm latest 6.9.0 Repo klarvo Slice is_prompt_echo

00 Auf einen Blick

Der wertvolle Kern von TDD funktioniert in BMAD real — aber der Generator ist auf JavaScript verdrahtet, der „rote" Zustand ist nur übersprungen statt beobachtet-rot, und nichts erzwingt die Reihenfolge. Der fehlende Hebel ist Durchsetzung, nicht eine weitere Regel.

Kernsatz
Ein Agent, der „einfach codet", liefert Code plus eine selbst-attestierte Behauptung, dass er funktioniert. Echtes TDD ersetzt die Selbst-Attestierung durch eine externe, vorher festgelegte, nachweislich fälschbare Prüfung. Genau diese Ersetzung ist in Stock-BMAD nicht durchgesetzt.

Der entscheidende Handgriff
Das Rot wurde durch erneutes Laufen im Vor-Fix-Zustand beobachtet — eine unabhängige Rot-Beobachtung, von Hand ausgeführt. Genau diesen Schritt erzwingt Stock-BMAD nicht.

03 Was glatt lief

Framework-Prereq erfüllt

Cargo deckt atdds Test-Framework-Anforderung — reine Rust-Kern-Logik ist echt test-first-bar.

Schnell & lokal

cargo test ~0,03 s, Linux-lauffähig — kein Gerät/Emulator nötig.

Gate-Logik solide

Deterministische Schwellen (P0 100 % / overall 80 % / P1 90–80) — sauber.

Skip-bewusst

trace zählt skipped/fixme/pending und senkt die Konfidenz bei null aktiven Tests — das Tooling kennt das Skip-Problem.

04 Bruchstellen — was Stock-BMAD verfehlt

AAuto-Detect → HALThoch

Wegen react in der package.json klassifiziert BMAD klarvo als fullstack → harte Prereq playwright.config fehlt → ein Stock-Lauf bricht ab, obwohl die Arbeit reiner Rust-Backend ist.

BRust nicht erkanntmittel

Backend-Prereq-Liste kennt nur conftest.py / *_test.go / .rspec — Rusts inline #[cfg(test)] fehlt, obwohl cargo grün läuft.

CGenerator nur JShoch

atdd dispatcht nur „API"- und „E2E"-Worker (test.skip(), Playwright). Kein nativer Rust/Backend-Unit-Pfad → das Rust-Rot muss der Operator schreiben.

D„RED" = übersprungenhoch

Der erzeugte Zustand ist test.skip() — weder rot noch grün. Das Rot materialisiert sich nur, wenn jemand un-skippt & läuft; nichts erzwingt das. = Wurzel von Issue #1784.

EKomposition manuellhoch

Mit Daten belegt: die 7-3-atdd-Scaffolds sind nicht im echten Baum — ein Mensch schrieb äquivalente Tests neu. atdd-Output landet im Output-Ordner, nie im Build. = Beschwerde #843.

FKein Rot-Beobachterhoch

Derselbe Worker schreibt Code und attestiert das Rot (Selbst-Attestierung). trace läuft erst nach Grün; ohne CI blockt der Gate nichts.

GStep 5/6-Widerspruchhoch

Step 5 „Write FAILING tests first" vs. Step 6 „Author comprehensive tests" (danach). Ein Worker erfüllt Step 6 und meldet wahrheitsgemäß „compliant", ohne je rot gewesen zu sein. In 6.9.0/main byte-identisch offen.

06 Fazit für eine generische TDD-Fähigkeit

Hinweis: Dieser Abschnitt ist Hälfte 2 — meine Schlussfolgerung, ungeprüft. Vor Umsetzung adversarial gegenprüfen.

  1. Der wertvolle Kern ist real — rot→grün auf einer Logik-Scheibe funktioniert und ist ehrlich beobachtbar. Aber der Generator emittiert nur JS; generisch braucht es native Test-Emitter (oder akzeptiert Operator-Scaffolds).
  2. Der fehlende Hebel ist Durchsetzung, nicht Anweisung. Die Rot-zuerst-Regel existiert (Step 5) und wird ignoriert. Lösung: ein unabhängiger Rot-Beobachter — eine nicht-implementierende Instanz, die mechanisch bestätigt, dass ein impl-freier Commit rot war, bevor der grüne kam.
  3. Unabhängigkeit ≠ zweiter Agent. Sie kommt aus Determinismus: ein Skript, das Git-Historie liest und Tests laufen lässt, kann nicht self-attestieren. Ein weiteres LLM-Skill wäre nur erneut überspringbar.
  4. CI ist die größte Design-Gabel. Mit CI ist der Beobachter gratis und der Gate ein echter Block; ohne CI gehört er in einen Git-Hook (lokaler, non-bypassbarer Trigger). Generisch darf CI nicht vorausgesetzt werden.
  5. Step 5/6-Widerspruch auflösen, damit „rot zuerst" und „umfassende Tests" eine geordnete Anweisung sind, nicht zwei widersprüchliche.

07 Was TDD beweist — und was nicht

✓ Ordnung

Test X war an Commit N rot, an N+1 grün → rot-zuerst bewiesen. Unbestechlich.

✗ Test-Wert

Ein vacuous-grüner Test fällt nicht auf. Separate Sorge (Inversions-/Mutationsprüfung).

Ehrliche Erwartung
TDD ist ein Boden unter dem Logik-Kern, kein Bug-Netz. Auf klarvos eigener Bug-Historie hätte es 0 von 3 echten Bugs sauber gefangen (Mikro-Pfad, Laufzeit-Pipeline, Plattform-Parität sind nicht unit-erreichbar). Nicht als „fängt die Bugs" verkaufen.
