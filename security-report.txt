[K-1] Content Security Policy deaktiviert
──────────────────────────────────────────
Datei:     src-tauri/tauri.conf.json, Zeile 25
Typ:       XSS / Code Injection
CVSS:      9.0 (Kritisch)

Befund:
  "security": { "csp": null }

CSP ist auf null gesetzt, was saemtlichen Schutz gegen XSS und Script-Injection
vollstaendig deaktiviert. In einer Tauri-App hat das Frontend ueber IPC-Commands
vollen Zugriff auf das Rust-Backend. Wird das Frontend kompromittiert, hat ein
Angreifer Zugriff auf:
  - Alle API-Keys im Config
  - Dateisystem-Operationen
  - Aufnahme-Pipeline
  - Lizenzvalidierung

Empfehlung:
  CSP aktivieren mit restriktiven Direktiven:
  "csp": "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'"
  'unsafe-inline' fuer Styles nur wenn noetig (Tailwind), niemals fuer Scripts.

[K-2] Test-Mode Lizenzvalidierung in Produktion deaktiviert
──────────────────────────────────────────
Datei:     src-tauri/src/license/ls_client.rs, Zeilen 171-177 und 221-230
Typ:       Authentication Bypass
CVSS:      8.5 (Kritisch)

Befund:
  // TODO(launch): Re-enable before public release!
  // #[cfg(not(debug_assertions))]
  // if lk.test_mode {
  //     return Err(LsApiError::Api(...));
  // }

Die Pruefung, ob ein Lizenzschluessel im Test-Mode ist, ist auskommentiert —
sowohl in activate() als auch in validate(). Dadurch werden Test-Lizenzen in
Production-Builds akzeptiert. Jeder mit einem Test-Key erhaelt vollen Zugang zu
allen Paid-Features.

Empfehlung:
  Code sofort wieder einkommentieren. Zusaetzlich einen CI-Check einrichten, der
  vor Release sicherstellt, dass dieser Block aktiv ist.

──────────────────────────────────────────

[K-3] Hardcoded Keystore-Passwort im Build-Script
──────────────────────────────────────────
Datei:     scripts/android-build.sh, Zeilen 209-210
Typ:       Credential Exposure
CVSS:      8.0 (Kritisch)

Befund:
  --ks-pass pass:dikta123
  --key-pass pass:dikta123

Das Keystore-Passwort fuer die Android-APK-Signierung steht im Klartext im
Build-Script. Obwohl die Datei in .gitignore gelistet sein mag, ist dieses
Muster gefaehrlich:
  - Jeder mit Repo-Zugang kann APKs als legitime App signieren
  - Kompromittierung der Signing-Identity ermoeglicht App-Impersonation

Empfehlung:
  - Passwort in Umgebungsvariable auslagern ($KEYSTORE_PASSWORD)
  - Keystore-Passwort rotieren und neuen Keystore generieren
  - Pre-commit Hook einrichten, der Klartext-Passwoerter im Code verhindert

[H-1] API-Keys im Klartext auf Festplatte gespeichert
──────────────────────────────────────────
Datei:     src-tauri/src/config/mod.rs, Zeilen 9-12
Typ:       Credential Storage
CVSS:      7.5

Befund:
  API-Keys (Groq, DeepSeek, OpenAI, Anthropic, Turso) werden als Plaintext in
  einer JSON-Datei im App-Data-Verzeichnis gespeichert. Der Code dokumentiert
  dies selbst als verbesserungswuerdig:

  "API keys are stored on disk as plain text inside the user-owned app-data
   directory. A future improvement could use the system keystore."

Risiko: Privilege Escalation, Malware oder Festplatten-Forensik legen alle
API-Keys offen.

Empfehlung:
  Windows Credential Manager / macOS Keychain / Linux secret-service nutzen.
  Tauri bietet hierfuer das Plugin tauri-plugin-stronghold.

[H-2] Sensible Umgebungsvariablen werden geloggt
──────────────────────────────────────────
Datei:     src-tauri/src/config/mod.rs, Zeilen 987-1038
Typ:       Information Disclosure
CVSS:      6.5

Befund:
  Beim Laden der Konfiguration wird fuer jede geladene Umgebungsvariable ein
  Log-Eintrag geschrieben:

  log::info!("[config] groq_api_key loaded from GROQ_API_KEY env var");

  Betroffen: GROQ_API_KEY, DEEPSEEK_API_KEY, OPENAI_API_KEY, ANTHROPIC_API_KEY,
  TURSO_URL, TURSO_TOKEN

  Zwar wird der Wert selbst nicht geloggt, aber das Vorhandensein wird
  offengelegt. In Kombination mit Log-Aggregation oder Crash-Reports koennte
  dies Information leaken.

Empfehlung:
  Log-Level auf debug herabsetzen oder Logging ganz entfernen.

[H-3] Android: Exportierte Komponenten ohne Schutz
──────────────────────────────────────────
Datei:     src-tauri/gen/android/app/src/main/AndroidManifest.xml, Zeilen 25, 53
Typ:       Android Component Exposure
CVSS:      6.5

Befund:
  <activity android:name=".MainActivity" android:exported="true">
  <service android:name=".KlarvoAccessibilityService" android:exported="true">

  MainActivity ist exported — andere Apps koennen sie direkt starten.
  KlarvoAccessibilityService ist exported mit BIND_ACCESSIBILITY_SERVICE
  Permission, was korrekt ist fuer AccessibilityServices, aber das exported-Flag
  vergroessert die Angriffsflaeche.

Empfehlung:
  MainActivity: exported="true" ist fuer LAUNCHER-Activities erforderlich, aber
  sicherstellen, dass keine sensiblen Intent-Extras verarbeitet werden.
  Fuer alle nicht-LAUNCHER Activities: exported="false" setzen.

[H-4] Android: Cleartext-Traffic moeglicherweise erlaubt
──────────────────────────────────────────
Datei:     src-tauri/gen/android/app/src/main/AndroidManifest.xml, Zeile 19
Typ:       Network Security
CVSS:      7.0

Befund:
  android:usesCleartextTraffic="${usesCleartextTraffic}"

  Der Wert wird ueber eine Build-Variable gesteuert. Wenn auf true gesetzt,
  erlaubt die App unverschluesselten HTTP-Traffic. API-Keys und Transkriptionen
  koennten im Klartext uebertragen werden.

Empfehlung:
  In Production-Builds explizit auf false setzen. Network Security Config
  hinzufuegen, die HTTPS fuer alle Domains erzwingt.

  for (col in listOf("uuid TEXT", "device_id TEXT", ...)) {

BEWERTUNG
──────────────────────────────────────────

  Die LLM-Cleanup-Pipeline ist hochgradig anfaellig fuer Prompt Injection.
  Alle 6 Injection-Surfaces sind verwundbar. Besonders kritisch:

  1. custom_prompt: Direkter Zugang zum System-Prompt, trivial auszunutzen
  2. voice_command/selected_text: Boeswillige Dokumente koennen Befehle
     einschleusen wenn der User sie markiert und "summarize" sagt
  3. raw_text: Gesprochene PI-Payloads werden von Whisper transkribiert
     und vom LLM als Instruktionen interpretiert
  4. dictionary_terms: Newline-Breakout aus dem Dictionary-Kontext moeglich

  Das Output-Detection-Framework erkennt alle getesteten Unsafe-Patterns
  korrekt, aber die App hat aktuell KEINE Output-Sanitization implementiert.

  Wichtig: Dies sind Schwaechen des LLM-Providers (Groq/Llama-3.3-70b),
  nicht primaer der App. Andere Provider (DeepSeek, OpenAI) koennen anders
  reagieren. Das Framework ermoeglicht den Vergleich:
    PI_PROVIDER=deepseek cargo test --test pi_security -- --ignored


================================================================================
  BESTANDENE PRUEFUNGEN (kein Handlungsbedarf)
================================================================================

[OK] SQL Injection (Rust-Backend)
  Alle Queries in history/mod.rs und sync/mod.rs verwenden parametrisierte
  Statements mit params![] bzw. TursoValue-Typen. Kein Injection moeglich.

[OK] XSS im Frontend
  Kein dangerouslySetInnerHTML, kein innerHTML, kein eval(). React's
  automatisches Escaping schuetzt alle dynamischen Inhalte. CSS-Injection
  wird durch textContent statt innerHTML verhindert (ThemeSwitcher.tsx).

[OK] Command Injection
  xdotool-Aufrufe (paste/mod.rs) verwenden ausschliesslich statische
  Argumente. Kein User-Input fliesst in Prozess-Aufrufe ein.

[OK] Path Traversal
  Model-Pfade (stt/model_manager.rs) stammen aus einem hardcodierten Katalog.
  Kein User-kontrollierter Input in Dateipfaden.

[OK] Deserialisierung
  JSON-Parsing nutzt sichere Methoden (serde in Rust, optString() in Kotlin).
  Keine unsichere Deserialisierung erkannt.

[OK] CSRF / CORS
  Als Tauri Desktop-App nicht relevant — Kommunikation erfolgt ueber IPC,
  nicht ueber HTTP. Kein traditioneller CSRF-Vektor vorhanden.
